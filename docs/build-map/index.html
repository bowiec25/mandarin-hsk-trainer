HSK Trainer Build Map: the architecture guide

A vocab trainer for HSK 3.0, bands 1–3 (the 2026 syllabus, 978 words), built from reusable blocks: small parts with one job each, a SPEC.md, code and tests. Generic parts live in quizkit (any quiz could use them); Mandarin parts live in hsk_trainer. State: after M5, 2026-11-10. Repo: bowiec25/mandarin-hsk-trainer.

0. At a glance

Start here. Think of the app as a little factory that turns a word list into a quiz. The blocks are its machines: script blocks follow fixed rules, agent blocks ask Claude when a job needs language judgment. The data files are the shelves between the machines: each machine takes from one shelf and puts on the next. The checks are inspectors at the doors: tests, scripts and GitHub stop bad work from passing. The subagents and hooks are helpers who build and inspect the factory while we work; they are never part of the app. The factory has five lines:

  • A · Data in: the word list is downloaded, checked and turned into 978 cards.
  • B · The quiz loop: cards are dealt (due words first), you answer, the engine keeps score, and your progress is saved in Leitner boxes (M5).
  • C · Grading: your answer is marked against Claude's answer list, and a Claude judge has the last word.
  • D · Sentences: Claude writes example sentences while you play; scripts check them; good ones are banked. In the translate modes the sentence is the question.
  • E · How we build: the routine and helpers that make and inspect every block.

1. The big picture: from the word list to you

One diagram. Box colours as in the legend above. The left half runs once, offline, and its files are committed. The right half runs every time you play. While you study, only two parts call Claude: the judge and sentence_writer's write_one (via live_sentences), each with an off switch.

2. The five workstreams

Each card is one strand of the picture above: what it does, its parts, its files, what it hands to the next strand, and how it is tested. "Script" = plain code that can be checked; "agent" = calls Claude for language judgment, and a script checks its output (ADR 0002).

B · The quiz loop

What it doesYou run uv run hsk quiz --band 1 --mode char --n 10: it deals the band's words (due words first, M5), shows each one, reads your answer, marks it, saves it and moves the word's Leitner box, and keeps score. Ctrl-C stops and keeps the score. --seed replays the same words; --no-save practises without saving. uv run hsk stats shows your boxes, what's due, the last 7 days and your most-missed words.
Progress (M5)

   ▼              │
answer marked ──► teacher (leitner): right = up a box, wrong = box 1
   │              │
   ▼              ▼
filing cabinet (progress_store) = data/progress.db  ◄── hsk stats (looks only)
5 boxes waiting 0 / 1 / 3 / 7 / 21 days, kept per word and skill (Mode.skill: the 4 word modes share recognise, the 2 translate modes share sentence). A new word answered right starts in box 2; "couldn't check" is saved but doesn't move the box (ADR 0013). Glue: quizkit/progress.py.
Partsdeck_builder (script, quizkit: level, how many, shuffle, due first) · progress_store (script, quizkit: the filing cabinet) · leitner (script, quizkit: the box rule) · engine (script, quizkit: QuizSession + run_quiz) · the CLI src/hsk_trainer/cli.py (Typer; not a block, it wires blocks to the keyboard) · modes as config: quizkit/modes.py + hsk_trainer/modes.py
ModesAll 6 play: char (hanzi) · char_pinyin (+ pinyin) · char_sentence (+ a sentence) · full (+ pinyin, sentence, sentence pinyin) · translate (a sentence to translate) · translate_pinyin (+ its pinyin). A mode is config: the fields to show, and where the answer comes from (answer_from: the card, or the sentence's English, ADR 0012). The engine's optional prepare hook turns each word into its sentence just before it's asked, or skips it.

Hands on toThe engine calls the grader for every answer and the judge (if given) when the grader says wrong. In the sentence modes the CLI wraps ask/tell with the sentence part.

C · Grading

What it doesTwo layers (ADR 0005–0007). 1. One answer list Claude wrote once, offline, checked by a script and committed. 2. Only when the list says wrong, a Claude judge is asked "is this right after all?", and its verdict is saved.
Partsanswer_writer (agent, hsk_trainer: batch, chunks of 40, Sonnet, --limit / --dry-run; load_answers reads the file back through the same checker) → grader (script, quizkit: forgives case, punctuation, "to", small typos) → judge (agent, quizkit: generic, any quiz passes one subject sentence; Haiku by default; an optional rubric: the word rubric, or GIST_RUBRIC for the translate modes, ADR 0012) · quizkit/claude.py (the shared claude -p helper) · quizkit/blocks/judge/eval.py (the eval script)
Filesout of answer_writer: data/generated/answers.jsonl (978 lines) + answer_writer_log.jsonl (model, prompt version, tokens) · judge: data/judge_cache.jsonl (gitignored; keyed by card, answer, answer list, model, prompt version) · eval sets: tests/data/judge_eval_hsk.jsonl (31 word cases) + tests/data/judge_eval_sentences.jsonl (33 sentence cases, gist rubric)
Hands on toThe CLI joins answers.jsonl onto each card, so the grader sees answers that are already typeable (ADR 0006). The judge's verdict ("✅ accepted by the Claude judge: …") is printed by the CLI's tell.
Tested byblocks/test_answer_writer.py (fake Claude; the real file passes for all 978 cards) · blocks/test_grader.py (toy data, no Chinese) · blocks/test_judge.py (fake Claude, injection cases) · test_judge_eval.py (counting only) · test_claude_helper.py · test_retired.py (the old rule cleaner stays gone) · the real eval by hand (section 7)

D · Sentences

What it doesIn char_sentence and full, each word comes with an example sentence. While you answer one word, Claude writes the next word's sentence; scripts check it; if it passes it is shown and saved to a bank that grows as you play (ADR 0008–0011).
Partssentence_validator (script: the word stands on its own, every other word at or below the band, 3–20 characters; reads with our own word list, not jieba, ADR 0009) + the pinyin check (every syllable is a real reading, ADR 0010) + the English check, both inside sentence_writer · sentence_writer (agent: batch top-up per band, chunks of 20, up to 2 retries with the reasons; and write_one: one word, one call, no retry, used live) · sentence_bank (script: new or banked by max(0.2, 1/(1+n)), least recently seen first, up to 10 a word) · live_sentences (script: background threads ask ahead, wait at most 15 s, switch off after 2 failures in a row, fall back to the bank) · data-auditor subagent (reads the bank for what scripts can't judge)
Filesdata/generated/sentences.jsonl (the bank, committed: 23 words / 40 sentences now, grows with play) · sentence_writer_log.jsonl (batch, committed) · data/live_sentence_log.jsonl (live, gitignored) · data/sentence_seen.json (when you saw each one, gitignored) · docs/audits/2026-11-05-sentences.md (first audit: 44 checked, 4 removed)
Hands on toThe CLI takes sentence / sentence_pinyin out of the mode before the deck is built, then prints the sentence under the word and its English after you answer. At the end, finish saves sentences still being written.
Tested byblocks/test_sentence_validator.py · blocks/test_sentence_writer.py (fake Claude; the real bank passes the checker) · blocks/test_sentence_bank.py · blocks/test_live_sentences.py (fake writer, slow and late paths) · test_cli.py (sentence modes) · the auditor's planted test, by hand

5. Agents and helpers

Everything that acts on its own: the app's agents, our building helpers, hooks and GitHub workflows.

Agent block: part of the app

  • Python in src/ that calls Claude itself, through claude -p
  • A block like any other: SPEC, code, tests (with a fake Claude)
  • A script always checks what it writes; it logs model, prompt version and tokens
  • Examples: answer_writer, sentence_writer, judge

Subagent: a helper for us, while building

  • A Markdown file in .claude/agents/, used inside Claude Code
  • Main Claude hands it a job; it reports back; never part of the app
  • Its tool list is a hard limit; its instructions are guidance
  • Examples: test-writer, block-reviewer, data-auditor
